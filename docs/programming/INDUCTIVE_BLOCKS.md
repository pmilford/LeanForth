## In plain words

A data type in Lean is given by its constructors, the ways of building an
element; Lean's kernel then derives the type's **recursor**, the
principle of induction and of definition by cases, together with
computation rules. An export file holds the type, its constructors and a
recursor, but the file's recursor is never trusted: LeanForth runs the
checks Lean's kernel runs on the type and its constructors, in Lean's
order, **builds the recursor itself** exactly as Lean's kernel builds it,
and compares it, field by field, with the one in the file. If the file's
recursor is not the one Lean's kernel would have built, the file is
rejected, as Lean's own checker of exports rejects it. Only then do the
type, its constructors and its recursor become usable by later
declarations, all at the same moment.

Task 5.2.1a covers a block of **one type that is not recursive**: no
constructor takes an argument of the type being defined. That includes
`Bool`, `True`, `And`, `Or`, `Exists`, `Eq`, `PUnit`, `PProd` and
structures such as `Add`. Task 5.2.1b adds **recursive types** such as
`Nat` and `List`, and *reflexive* ones, whose constructors take a
function into the type: Lean's kernel first checks that the type occurs
in each constructor only *strictly positively* (never to the left of an
arrow), and the recursor then has an **induction hypothesis** for each
recursive argument. Mutual blocks (types defined together) and nested
ones (a type used inside another, as in `List Tree`) are a later task
(5.2.5) and are answered *unsupported*, and so is everything that uses
them.

## Example in three forms

Conjunction, the structure `And` (ADR 0015, §1).

- **Mathematics.** A proof of $a \wedge b$ is a pair of proofs. Its
  recursor: from $f : \forall (x : a)(y : b),\ C\,(x, y)$ we get $C\,t$
  for every $t : a \wedge b$, with $\mathrm{rec}\,f\,(x, y) = f\,x\,y$.
- **LeanForth words** (ADR 0017 §15 *sketch syntax, not implemented*:
  LeanForth reads data types from Lean exports only):

  ```text
  structure MyAnd
    Prop explicit: a
    Prop explicit: b
    Prop
  where
    a explicit: left
    b explicit: right
    MyAnd a $ b $  constructor: intro
  end MyAnd
  ```

- **Lean.** `structure And (a b : Prop) : Prop where intro :: left : a;
  right : b`. The kernel generates

  ```text
  And.rec.{u} : {a b : Prop} → {motive : a ∧ b → Sort u} →
    ((left : a) → (right : b) → motive ⟨left, right⟩) → (t : a ∧ b) → motive t
  k = false; rule And.intro, 2 fields: fun a b motive intro left right => intro left right
  ```

What LeanForth does with Lean's export of it
(`tests/core/check-block-cases/ind.and.ndjson`, the row `ind.and` of the
inductive table): it reads the one-line block record
`{"inductive":{"types":[…],"ctors":[…],"recs":[…]}}`, checks the type
`Prop → Prop → Prop` and the constructor, finds that the result is a
proposition with one constructor whose two fields are proofs (so the
recursor may eliminate into every universe, rule E3, and gets its own
universe `u`), builds `And.rec`'s type and rule as above, finds them equal
to the file's, and publishes `And`, `And.intro` and `And.rec` together:
`make test-check-block` prints nothing for it but checks *accepted* at
step 15. Change the file's rule to `fun a b motive intro left right =>
intro right left`, and the same check rejects the block at step 13 (rule
B3, Lean's replay: "Invalid recursor").

## A recursive example in three forms

The natural numbers (ADR 0015, §1), the row `ind.nat` of the table.

- **Mathematics.** ℕ is generated by $0$ and $n \mapsto n+1$. For every
  family $C : ℕ \to \mathrm{Sort}\,u$, from $z : C\,0$ and
  $s : \forall n, C\,n \to C\,(n+1)$ we get $\mathrm{rec}\,z\,s :
  \forall n, C\,n$, with $\mathrm{rec}\,z\,s\,0 = z$ and
  $\mathrm{rec}\,z\,s\,(n+1) = s\,n\,(\mathrm{rec}\,z\,s\,n)$. The
  hypothesis $C\,n$ of $s$ is the *induction hypothesis* of the
  recursive argument $n$.
- **LeanForth words** (ADR 0017 §15 *sketch syntax, not implemented*):

  ```text
  inductive MyNat
    0 Type
  where
    MyNat  constructor: zero
    MyNat explicit: n  MyNat  constructor: succ
  end MyNat
  ```

- **Lean.** `inductive N where | zero : N | succ : N → N`. The kernel
  generates

  ```text
  N.rec.{u} : {motive : N → Sort u} → motive N.zero →
    ((a : N) → motive a → motive a.succ) → (t : N) → motive t
  rule N.zero, 0 fields: fun motive zero succ => zero
  rule N.succ, 1 field:  fun motive zero succ a => succ a (@N.rec motive zero succ a)
  ```

LeanForth finds `succ`'s field `a : N` *recursive* (its type, put in
whnf, is an application of `N`), gives the minor premise its hypothesis
`motive a`, puts the recursive call `@N.rec.{u} motive zero succ a` into
the rule (at Lean's recursor levels: the motive's `u` first), and finds
the result equal to the file's `N.rec`. A constructor `mk : (N → Nat) → N`
(`N` to the left of an arrow, the row `pos.negative`) is rejected at step
9 with diagnostic 79, as Lean's kernel rejects it ("non positive
occurrence"): such a type would let a proof of `False` be written.

Not run: G4, Lean's defensive check of its own recursors (829–866), is
replaced by the comparison with Lean's recursor (B3): each rule's result
is the minor premise applied to the fields and to the recursive calls
`fun xs => T.rec As motive minors ks (u xs)`, whose types are the minor
premise's induction hypotheses by construction, so its type is the
recursor's result type.

**Positivity (task 5.2.1b; P1, P2, `check_positivity` 436–452).** For
each field whose type mentions the block's type (`T`), after its
universe check as in Lean: the type is put in whnf; if no occurrence is
left, the field is not recursive; a Pi whose domain mentions `T` is
*nonPositive* (diagnostic 79, rejected), otherwise its body is checked
one binder deeper; anything else must be a valid application `T As is`
(`is_valid_ind_app`: `T` at the block's universe parameters, the
parameters as its first arguments, indices that do not mention `T`), a
recursive field, or it is *nonValidOccurrence* (diagnostic 80). A field
whose type does not mention `T` is not tested: reduction never makes an
occurrence (`T` is in no environment a definition unfolds into), so
Lean's test passes on it whatever whnf gives.

**Where Lean puts a term in whnf** (step 8's telescope, positivity, a
recursive field's type when the recursor is built), LeanForth reduces
with whnfB and goes on only where Lean's whnf provably stops there
(`lf-blk-left?`): a Sort, a Pi, a lambda or a variable head, `T` itself,
or a constant declared as an inductive type, a constructor, an axiom or
an opaque constant and named none of the Nat operations Lean's
`reduce_nat` computes by name. Any other head -- a definition or theorem
Lean would unfold, a recursor or quotient Lean might reduce -- leaves
the block *unknown* (diagnostic 64) until plan task 4.2.2 (whnf with
delta and iota) is on main (rows `pos.through-definition`,
`pos.erased-by-definition`).

**Recursive fields and induction hypotheses** (`is_rec_argument`
426–433, `mk_rec_infos` 690–709, `mk_rec_rules` 770–785). A field is
recursive when its type, put in whnf binder by binder, ends in an
application of `T`; its hypothesis takes the domains of those binders,
stripped of type annotations, and the end's indices. The builder
(`inductive-recursor.fs`) keeps them per constructor in growable tables
and builds the terms with bound variables, each piece shifted from the
constructor's context to its place in the recursor.

**Lean's local types.** Lean gives each parameter, index and field the
type of its binder with outer `outParam`, `semiOutParam`, `optParam` and
`autoParam` removed (`consume_type_annotations`); LeanForth does the same
when it builds the recursor and when it types the constructors' fields.

**Where Lean might unfold, LeanForth says unknown.** Definitional
unfolding is phase 4. A telescope or a field type headed by a definition
(for example `outParam (Type w)` in `HAdd`), or a parameter domain that is
equal to the type's only after unfolding (`id Type`), leaves the block
*unknown*, never rejected.

**Comparison (B3).** Constructors first, then recursors, as Lean's replay:
a constructor's universe parameters, index, `numParams` and `numFields`
(its name, type and type name are the kernel's own, by B0); a recursor's
name (`T.rec`, else "No such recursor"), universe parameters (the motive's
universe first, `u` or `u_1`, … when taken), type, `all`, `numParams`,
`numIndices`, `numMotives`, `numMinors`, rules (constructor, `nfields`,
right side) and `k`. Terms compare structurally (`mixed-compare.fs`): the
store keeps no binder names or annotations, which Lean's `==` ignores.

**Publication (B5).** The check's candidate covers all the block's
members (`lf-env-span!`, `environment.fs`); the publisher re-checks every
member (kind, safety, no value, its block, distinct universe parameters,
every name unused below the block, also as a generated recursor),
writes every slot with the one outcome, the input declaration, the shared
dependencies and, for an accepted block, its B4 warning bits, and marks
them final last (`env-publish.fs`). The serial run skips the members
already final.

**Lean's generated recursor, when no slot holds it.** Lean's
`add_inductive` adds the recursor `T.rec` it generates to its environment,
whatever the file holds; Lean's replay accepts a block without it (B4).
A slot is an input declaration, one per record of the file, fixed when
the environment is made, and the generated terms are the check's
scratch, given back after it; so LeanForth keeps a *recipe* instead (ADR
0015 decision 12): the block check leaves on the block's slots whether
the recursor eliminates into every universe and whether the telescope it
walked after whnf was the raw one (`lf-env-recipe!`). A later lookup of
`T.rec` that no slot holds answers (-1 ok), the type's slot given apart
(`lf-env-genrec-of`; the log's resolve step names no slot, and the
outline says the kernel generated it), and inference checks the use's
universe arguments against the recursor's own (L1: the motive's first,
when it has one, then the block's), checks them (L2), records the block
as the dependency, and builds the recursor in its own scratch *at those
arguments*, from the block's input, with the same builder
(`generated-recursor.fs`, `inductive-recursor.fs`
`lf-recursor-build-at`): the motive's Sort at the first argument, the
block's constants at the others, and every binder domain read from
instances of the block's type and constructor types in which the block's
universe parameters are replaced by those arguments
(`lf-mixed-level-substitute`; review rvI21 R5-1). Building only copies
the domains and adds the constants and the motive's Sort, so the result
is the recursor's type instantiated, as Lean's `instantiate_type_lparams`
gives it; the rows `after.eq-at-*`, `after.exists-at-*` and
`after.universe-max-at-*` check it at renamed, concrete, swapped and
applied (eta) universes, where the domains mention the block's
universes. For a recursive block (task 5.2.1b) the builder finds the
recursive fields again on those instances, so the generated recursor has
its induction hypotheses (rows `after.nat-*`, `after.list-*`,
`after.reflexive-*`, `after.binary-tree-*`); only its type is built, as
a later declaration needs nothing else. A rebuild during another block's
check copies that block's record and its parameter domains aside and
gives both back (row `after.list-left-out-then-lookup-during-param-block`;
before task 5.2.1b the domains were overwritten, and such a block was
*invalid*). No universe name of the recursor's own is ever made, so its
motive's `u` need not be a level of the file (review rvI21 R4-1), and its
universe parameters have no limit of their own (R4-3: a block of 70 is
tested). A block without a recipe -- one whose
type is a Sort only after whnf, such as `(fun x : Type 1 => x) Type`
(row `after.redex-type-left-out-then-use-rec`) -- leaves a use of its
`T.rec` *unknown* (diagnostic 77) until task 4.2.2 brings whnf and
unfolding to a lookup (steps 4.2.2b-e). A file that uses `T.rec` and
declares it nowhere is loaded (ADR 0016 amendment 1) and checked as Lean
checks it.

The environment also *reserves the name* (`environment.fs`,
`lf-env-reserving`; review rvI21 B2): a name `P.rec` is held by every earlier inductive type
named `P`, and `P.rec_<digits>` (the auxiliary recursors of a nested
block) by every such type not accepted, since no accepted block is nested
yet (plan task 5.2.2 must hold those names for the nested blocks it
accepts). N2 (`lf-env-fresh`) treats a held name as declared when the type
is accepted (Lean's `alreadyDeclared`: the rows `after.*`), K5 when it is
undecided or unsupported, and *invalid* (too early) while it is open; the
publisher's re-check and the scheduler's readiness (`lf-env-ready?`) see
the same.

**The block's own type during the check.** Lean adds the type to its
environment before it checks the constructors. LeanForth's inference finds
it through a hook in `env-signature.fs` (`lf-envsig-local`), set by
`check-block.fs` and answering only during a block's step 9 and, in depth,
only while the declaration checked is the block's first member (review
rvI21 M1), with L1 and L2 as for any constant and no dependency.

**A guard in comparison (P4).** With structures in the environment,
Lean's last comparison route, `is_def_eq_unit_like`, makes any two terms of
a structure like `PUnit` equal. Rules D3 and D5 of
[ADR 0011](../adr/0011-definite-rejection.md) therefore no longer call two
variable-headed terms apart unless the left one's type is visibly no
constant application (`lf-minfer-unit-free?`, `mixed-infer.fs`). Without
it, `fun x y P h => h : ∀ x y : PUnit, ∀ P, P x → P y`, which Lean
accepts, would be rejected (row `unit.punit-variables`). With the
derivation log on, the aside inference's steps are logged as premises of
the step they serve; the log copies each scratch term into its own pools
when it writes the record (identity checked, `core/derivation-log.fs`), so
the proof outline never prints a node the aside gave back (review rvI21
L4). The guard is a temporary gap until task 5.2.2 (structure eta and
unit-like comparison): it can only turn *rejected* into *unknown*, never
the other way.

## Data in the input

The feed (`src/import/feed.fs`) gives each block a header and each member
its exported data in `lf-input-more` (`src/core/input.fs`): a type's
`numParams`, `numIndices`, `numNested`, flags, `all` and `ctors`; a
constructor's `induct`, `cidx`, `numParams`, `numFields`; a recursor's
numbers, `k`, `all` and rules (constructor, `nfields`, right side as a
term). `lf-input-add` checks that every record lies within the data; the
data is in the input's fingerprint. Only the feed path carries blocks.
Since 2026-11-04 `bin/leanforth check` stages and feeds the export
([the command line](../user/COMMAND_LINE.md#an-inductive-type)), so its
blocks get the checker's verdicts there (`tests/cli/inductive.ndjson`: a
block, a theorem and a definition by its recursor, all accepted, as Lean
accepts them). `check --record`, `replay` and `print` still read with
`import/checker-input.fs`, which refuses an inductive type while reading
(*unsupported*): a temporary gap, closed for `check --record` and
`replay` by a run record version for exports of any size (plan task
6.5.2, [run records, version 0.2](RUN_RECORDS.md#version-02-records-of-any-size))
and for `print` by moving it onto the feed (plan task 3.4.1).

## Limits

Each limit below is a difference from Lean's verdict in the default mode,
temporary, with the task that closes it (the owner's rule of 2026-11-04:
the default is exactly Lean):

- **Capacities, *full* where Lean decides; task 6.2.0** (the dynamic
  limits): at most 512 constructors per block (`lf-ind-ctor-capacity`: a
  block with more is *full*, every member, found when the block is
  opened, before anything is written for its constructors, diagnostic 76;
  review rvI21 B1); parameters plus indices, and the fields of one
  constructor, at most 64 (inference's binder context); a check records
  at most 16 dependencies (`lf-env-dep-capacity`, for every declaration).
- **A whole file refused, *invalid*, where Lean gives a verdict per
  declaration; task 5.2.6** (a plan row added for it): a file that names a
  constant no declaration has (other than a recursor a block of the file
  generates), or that holds an inductive record with constructors or
  recursors but no type. Pinned Lean 4.35.0 (2026-11-04): the declaration
  naming an undeclared constant is rejected (`unknownConstant`, by the
  kernel and in replay); a constructor or recursor whose type is not in
  the file is refused by replay ("No such constructor", "No such
  recursor"); the rest of the file is checked. The table's rows
  `names.reserved-nested-prefix` and `quotinit.without-eq` are such files.
- **A type that is a Sort only after whnf, *unknown*; task 4.2.2** (steps
  4.2.2b-e, whnf and unfolding in inference): a use of the generated
  recursor of such a block (above), and in general a binder whose type's
  type is a Sort only after whnf (inference gives *unknown*, diagnostic
  32, where Lean's `ensure_sort` reduces).
- **The P4 guard, *unknown* where Lean rejects; task 5.2.2** (structure eta
  and unit-like comparison).
- **Positivity and recursive fields through definitions, *unknown*; task
  4.2.2** (whnf with delta and iota, agent U4's port): a field type whose
  whnf Lean reaches by unfolding a definition or reducing a recursor
  (`id (Bad → Nat)`, `Function.const Type Nat Ok`), and a type's
  telescope ending in such a head. Once 4.2.2's `whnf` is on main, the
  block check calls it there.
- **Iota (R1) with literal majors (L2); tasks 4.2.2c and 5.2.3**: Lean
  reduces a recursor applied to a constructor in `whnf_core`; agent U4's
  port of whnf leaves a hook for it, and 5.2.1b's iota goes behind that
  hook once it is on main. Until then a check that needs it is *unknown*
  (rows `iota.*` are *unsupported* anyway: they use literals, task 5.2.3).
- **Mutual and nested blocks, *unsupported*; task 5.2.5.** The nested
  test (step 1) may only find more than Lean: when the earlier type is
  not usable, any argument mentioning `T` counts.
- **A field type without an occurrence of `T` is not put in whnf**
  (positivity, step 9). Lean's `check_positivity` reduces it and drops the
  result; the two can differ only if that reduction fails with a resource
  exception (`deepRecursion`, the Nat literal size limit), which Lean
  turns into a rejection. An open question for the owner (report of task
  5.2.1b); task 4.2.2's whnf can close it.
- A block rejected only by B3 still takes its names. Lean's replay runs
  its comparison after its kernel added the block (`addDecl` first, the
  postponed checks of constructors and recursors last), so the type, its
  constructors and `T.rec` are declared although the file's records are
  refused. The block check says so (`lf-env-added!`, step 13 rejected);
  the publisher marks the type's and constructors' slots
  (`lf-slot-added?`), not the file's recursors, which the kernel may not
  have added (a renamed one); and the type holds `T.rec` as an accepted one
  does. So a later definition of one of those names is rejected as Lean's
  `alreadyDeclared` (review rvI21 R2-1). And the block's type and
  constructors are usable by later declarations, as Lean's later
  declarations meet the kernel's constants (the owner's condition of
  2026-11-04): the publisher re-checks and records such a block as an
  accepted one, each constructor with the type's universe parameters (as
  the kernel declares it, whatever the file's record says), lookups find
  the slots usable (`lf-slot-usable?`), and `T.rec` is the generated
  recursor, as above; the block's own outcome stays *rejected* (rows
  `after.b3-*`). Their types were checked by steps 1–12. A block the
  kernel itself rejects (any earlier step) takes no name and adds nothing,
  as in Lean.
- A recursor missing from the block (B4) is accepted, as Lean's replay
  accepts it; its name is reserved, as above, so a later definition of it
  is rejected as Lean rejects it, and a later use gets the generated
  recursor, also in a file that declares it nowhere. Only a tampered file
  can do this: lean4export writes every recursor.
- The published slots of an accepted block hold the file's own data
  (`lf-idecl-more`): its recursors' numbers, `k` and rules, and its
  constructors' numbers, equal LeanForth's (B3 compared them); the type's
  `numIndices`, `isRec`, `isReflexive` and `numNested` are the file's and
  untrusted. LeanForth's values are the recursor's `numIndices`, Lean's
  `is_rec` and `is_reflexive` as the audit computes them (since task
  5.2.1b) and `numNested` 0; the warning bits on the slots
  (`lf-env-warnings`) say which of the file's differ. No check reads
  these fields yet; task 5.2.2 (structure eta needs "not recursive"),
  the first to read them, must use LeanForth's values (ADR 0015 B5).
- A scheduler that checks declarations in parallel must skip a block's
  later members, as `lf-env-next` does (each would otherwise start a check
  of its own and fail closed as *invalid*), and must ask `lf-env-ready?`,
  which also waits for the types that may hold a name `T.rec`.
- B0's distinct-name test and C4 compare names pairwise without fuel:
  quadratic in the block's members. The constructors are at most 512; a
  header with very many types still reaches B0 before the scope check
  makes it *unsupported*.
