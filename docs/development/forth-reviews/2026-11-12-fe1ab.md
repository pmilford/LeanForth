## Gate answers

### [parser]: can natural text mean anything other than Lean's macro expansion?

No, as far as I could find, and nothing natural is accepted today.

- **Nothing completes.**
  - `end` of every natural declaration stops with error 71 (unsupported). Kinds checked: theorem, def, axiom, import-stub.
  - Tactic words stop with error 72 in both forms.
  - Kernel-form words in natural text stop with error 70.
  - Natural text that declares nothing gets error 49 from `leanforth check`.
- **Trees.**
  - `+ * = ≤` build `binop% HAdd.hAdd`, `binop% HMul.hMul`, `binrel% Eq` and `binrel% LE.le`. These are Lean's own macro rules.
  - A load-time check ties each operator word to the printer's notation table.
  - Arguments go into the application in Lean's order. `' NAME` takes no arguments. `$` adds one argument to an application made by a name, as Lean's `id g x` does.
  - `check_front.py` compares 6 statements with pinned Lean's `expandMacros`, and its self-test tells a wrong tree apart. I ran it: equal.
- **Argument counts.**
  - For a library constant, the count is the number of explicit (default) binders of its declared type.
  - The count is -1 when the end of that type may unfold: a definition, a projection, metadata or a let.
  - For a variable, the count is 0, or -1 when the head of its type is a definition, an operator node or a numeral.
  - Lean's count (`getFunInfo` after `whnf`) can only add binders. So the reader's count is never larger than Lean's.
  - A smaller count leaves extra values on the stack. The checks "exactly one statement", "exactly one proof" and "no gap between binder frames" then refuse the text.
  - So a text that has a valid reading under Lean's counts never has a different valid reading under the reader's. Miscounts fail closed (L1 for the error class).
- **Numerals.**
  - A numeral keeps its value and the position of its token, through a position stack kept beside the data stack.
  - Proof text sees no Forth word, and every consumer takes from the top, so the two stacks stay in step.
  - More than 9 digits, and number forms such as `0x3`, are refused (error 35).

### [bypass]: can a metavariable or a syntax tree reach the kernel or the export?

No.

- `lf-author-export` checks `lf-holes?` (any metavariable tag in the term or level store) before writing any line, and returns invalid. A test checks the outcome and that 0 lines were written; fault `fe-mvar-to-kernel` is caught.
- Two more barriers stand behind it:
  - the writer refuses term tag 16 and level tag 5 (unsupported, its default arms);
  - the importer stage has no metavariable record kind.
- The stores are emptied (`lfc-empty`) before the feed.
- The new tags 16 (term) and 5 (level) collide with no existing tag.
- Syntax trees live in their own store, which the export never reads. Natural declarations never get a type or value in the declaration records, and a failed text is never exported.
- `src/front` loads neither `kernel/` nor `import/`, and has no word that publishes, writes an environment slot or writes a verdict.

- `tests/author/fixtures.golden` is unchanged: terms, records and round trips of all 25 fixtures.
- `make reference-author`: 56 declarations from 19 fixtures, records equal to pinned Lean's; 24 of 24 faults caught.
- The marker is written on line 1, before the existing comment, so line numbers keep.
- The CLI cases differ only in the column shift on line 1.

## Findings

### M1, medium, process: the plan and progress pages are stale

`docs/project/PLAN_DRAFT.md` still says "not started" for FE1a and FE1b (lines 686-687). `docs/project/PROJECT_PROGRESS.md` (lines 40-41) says "designed 2026-11-12, no code".

AGENTS.md requires the status to change in the same commit. Use the done checker's stages ("tested alone").

### L1, low: two library argument-count cases misclassified or untested

Fault `fe-unfold-ignored` (a type ending in a definition's application) is listed as a gap "until FE1c". It can be closed now. My probe:

```lean
def F (α : Type) : Type := α → α
axiom c : F Nat
axiom d : (fun α : Type => α → α) Nat
```

Compiled and exported with pinned Lean's `leanexport`, then run with `bin/leanforth check --no-manifest --env`:
- `x c x =` gives error 73 (unsupported, exit 2), which is correct;
- `x d x =` gives error 18 (invalid, exit 4) at `:=`.

`lfc-unfolds?` (`check-lf.fs`) treats an application headed by a lambda as not unfolding, but Lean's `whnf` beta-reduces it. It fails closed, but with the wrong class.

Fix:
- treat lambda heads (tags `tag-lam` up to `tag-pi`) as unfolding;
- add this export as a fixture, with both tests;
- remove the gap entry.

### L2, low: robustness of the metavariable context

- **Unbounded memo read.** `dw-done?` (`dag-walk.fs:45`) reads the walk's memo with no bounds check; `dw-in?` runs only later, in `dw-descend`. A child at or past the memo size would read past the heap block.
  - That needs a stale assignment value, which `lf-mctx-reset` prevents. But nothing calls `lf-mctx-reset` yet: the context is not wired to the run.
  - Fix: `: dw-done? ( node walk -- flag ) 2dup dw-in? if dw-state 1 > else 2drop false then ;`
  - Call `lf-mctx-reset` from the store resets (`lfa-stores-reset`, `lfn-fresh`) when FE1e uses the context.
- **Orphan leaves.** `lf-mvar-new` and `lf-level-mvar-new` make the leaf before claiming the record. When the record store is full they leave an orphan leaf, so the test comment "changing nothing" is not accurate. It is fail-closed: the export refuses any leaf. Claim the record first, or correct the comment.

### L3, low, carried to FE1e: operator names are hygienic in Lean

Lean writes `HAdd.hAdd✝` and `Eq✝`: hygienic names that always mean the global constants. `check_front.py` strips the `✝` marks, and the syntax node stores a plain name ID.

FE1e must resolve operator names at the root, never through `namespace`, `open` or local binders. Say so in the `syntax.fs` header and test it in FE1e.

### L4, low: test and documentation gaps

- The numeral position stack's capacity (512 positions, error 64, full) is untested.
- Natural text against a snapshot library (`lfc-arity` on a snapshot's tier) is not in the suite. My probe works: `n Eq.refl` reads with arity 1; `Eq.refl` alone gives error 3.
- COMMAND_LINE.md's `print --lf` section does not say the text starts with `kernel-form`.

### Notes (no action now)

- `lf-holes?` refuses the whole run if any metavariable node exists anywhere in the stores. That is stricter than D2's "a declaration that contains one", and it matches a writer that writes every node. FE1f will need reachable-only writing or a fresh store, or every elaborated declaration will be refused.
- A walk's memo has one cell per node index, `lf-term-base + lf-term-count` cells. That is fine while authoring (base 0). Revisit if FE1c walks run with the input fed.
- The coverage reasons for the four front files share one text. The never-run blocks I measured match it: heap and load refusals, the out-of-range child, the default finder.
