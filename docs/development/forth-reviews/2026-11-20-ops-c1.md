## Fail-safe (priority 2)

- **Instance side (mkPath).**
  - The discrimination tree is built from the data's keys, which are Lean's own: `it-keys`, instances.fs:165.
    LeanForth's recomputed path only verifies them.
  - Equal: verified. Different: the data is refused (113, invalid). Unsupported: unverified, answered unsupported
    when a search tries it.
  - So a wrong key here can never add, drop or move an instance in the tree. It can only fail closed (see L1 for the
    size of that failure).
- **Query side (getUnifyKeyArgs).** LeanForth's own keys choose the branches visited.
  - A key more specific than Lean's loses candidates. An example would be GE.ge kept where Lean unfolds to LE.le.
  - A key less specific than Lean's adds candidates. A wrongly taken unfolding into a metavariable head, a star
    below the root, visits every child; fault M6 shows the shape.
  - Either can change which instance is found first, since a lost first candidate lets a later one that also
    unifies win. Every candidate is still unified with the goal by LeanForth's isDefEq and its subgoals solved, so a
    returned instance is always a well-typed solution as LeanForth judges it. It need not be the one Lean picks.
  - The consequence is a fidelity one: an elaborated statement or term that differs from Lean's. It is not
    soundness: nothing in discr-keys.fs reaches the kernel's verdict except through the finished term, which the
    kernel checks.
  - The guards against a differing statement:
    - check.py compares terms node for node with pinned Lean on decide's slice;
    - check_synth.py compares 16 candidate lists with pinned Lean's traces (3 new);
    - fault `fe-decide-skip-whnf-mul` shows the kernel rejects an unreduced `6 * 7 = 43`.
