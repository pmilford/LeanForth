## Answers to the questions

### Is every allocation a context owns freed exactly once, on every path?
Yes, as far as traced.
- Normal end (context-free): context-freeable first aborts on a non-context, the main context or an owned context. If
  the context is current, the task goes back to the main context. context-torn runs every teardown word once, then
  context-discard zeroes the size field and FREEs the block once. The result is the first nonzero code of the
  teardowns, else FREE's ior.
- The built-in teardowns (slabs-free, walks-free, frames-free) free a block only when its pointer is nonzero and zero it
  afterwards: idempotent, and safe on zeroed members.
- A THROW inside a check: the context stays allocated and owned until job-wait releases it; a later context-free runs
  the teardowns, which free whatever blocks the members hold.
- A cleanup word that throws, or has a wrong stack effect: teardown-call runs it under CATCH through call-balanced; the
  loop continues with the next teardown, and the block is still freed. The code returned is the first one
  (context-unbalanced for a wrong stack effect). Inherent limit, as the header says: a teardown that throws part way
  may leak the rest of its own blocks.
- context-new failing part way: ALLOCATE refused gives ( 0 ior ), nothing held. An initialiser or setup word throws
  (context-fill, under CATCH, restoring the current context): context-made runs every teardown over the partly
  initialised context, whose members not yet reached are zeroed, then discards the block once; it gives ( 0 ior ),
  where ior is the earliest nonzero of setup, teardown and FREE. No handle escapes.
- The main context is never freed; its blocks live until exit, as documented.
- Double free: only through a stale handle passed to context-free twice, documented undefined use; context-discard's
  zeroed size field catches the common case.

### Is the newest-first order guaranteed?
Yes. teardown-link-in prepends to layout-teardowns and teardowns-run walks from the head, so the built-in teardowns run
last. Every teardown runs with the context selected afresh (teardown-in). A fault reversing the list is caught, and so
is the existing context-teardown-selected-once.

### Is it safe with the job pool's per-task contexts?
Yes. lf-context and lf-owner are USER variables on both hosts (probe: Gforth 1.0.0 up@ + 496; Gforth 0.7.3 next-task +
224). Workers reset both cells at start (task.fs worker-run) and job-run restores them after each job. Contexts are
made, freed, claimed and released only outside jobs (context-outside-job aborts inside one); an owned context cannot be
freed, and only the driving task sets or clears owners. The layout and the teardown list are read-only after the seal.
Blocks a worker grew are freed by the main task after job-wait, safe with Gforth's thread-safe malloc.

### Stack effects and outcomes
They match the documentation: context-new ( -- context ior ), context-free ( context -- ior ), context-teardown ( xt -- )
(aborts after the seal), context-catch, context-claim and context-release. call-balanced detects a changed depth or a
changed x below (a word replacing x with an equal value cannot be detected, inherently). allocate0 and ior-earlier are
correct. One gap: the "first code" promise is not tested (L1).
