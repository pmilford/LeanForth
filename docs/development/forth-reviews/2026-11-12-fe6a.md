## Findings
### M1, medium: "equal up to binder names/info" is real, but it also hides real binder differences
Lean's `Expr` equality and hash ignore binder names and binder information, and lean4export shares terms by them, so
an export can show another term's names and infos: the "alike" class is a genuine property of the export. But
LeanForth reads its input (the recursor) from that same export, so its built definitions carry whatever names and
infos the export gave the recursor, and comparing with the export cannot show where those differ from Lean's
environment. Of the 197 alike definitions, at least 5 differ in binder information, not just names; 125 types have no
binder difference at all (only the value differs). Binder sequences dumped for six, from LeanForth and from pinned
Lean's environment (`getConstInfo`, `eraseMacroScopes`): `Subtype.casesOn`, `Add.casesOn`, `Inhabited.casesOn`,
`Option.casesOn` are exactly Lean's where the export differs; `Equivalence.casesOn` and `recOn` are not: LeanForth has
`refl: a:0`, `symm: a:0 b:0`, Lean `refl: x:0`, `symm: x:1 y:1` — the `symm` field's binders explicit in LeanForth and
implicit in Lean, copied from the export's own `Equivalence.rec`. In the unshared Init slice LeanForth equals Lean
exactly. The kernel ignores names and infos, so no trust issue, but it limits the fidelity claim (owner decision 7,
identical terms); the front end needs exact binder information once it elaborates applications of `casesOn`. Fix:
state the limit in constructions.fs's header and FRONT_END.md; add a reference check against Lean's environment over
all Init `casesOn`/`recOn` (names and infos); plan an exact source of binder names and infos (elaboration data, or an
export without sharing) before the front end uses these definitions.

### L1, low: the out-of-room paths are untested
50 never-run blocks in constructions.fs and 12 in expr-remap.fs (tier, tuple or heap growth refused; refusals Lean's
recursors never reach); only fuel exhaustion is tested. Eight of these paths read: no stack bug found. Add a tier or
heap that refuses on demand and test each "full" branch for outcome and stack depth.

### L2, low: the value comparison of `aux-alike?` is never tested
A fault comparing only types and parameters survives tests/front/constructions.fs. Add a case with alike types and
different values.

### L3, low: `recOn` and `casesOn` disagree on a Sort that needs reduction
`isPropFormerType` reduces (`forallTelescopeReducing`); `prop-former?` reads the type syntactically. `casesOn` refuses
such a type (`no-sort`); `recOn` silently takes the generic path where Lean might build it from `casesOn`. None on
Init. Apply the same `no-sort` refusal before `recOn` chooses its case.
