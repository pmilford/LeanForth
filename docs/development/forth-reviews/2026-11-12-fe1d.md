## Findings
- M1 (medium; settle before FE1e uses the data; [parser] gate): the reader checks names and kinds only.
  - The link from an instance or default instance to its class is not checked against the export. Lean's addInstance and addDefaultInstance take the class from the instance's type: the head of its conclusion after forallTelescopeReducing. So a record "class Mul, name instAddNat" passes.
  - Priorities, default-instance choices and reducibility statuses cannot be checked against the export at all. They rest on the data coming from pinned Lean, bound to the export only by an unkeyed SHA-256.
  - ELABORATION_DATA.md ("checked record by record against the export") and the module header read as a stronger guarantee. Say that names and kinds are checked, and that Lean-only facts are pinned Lean's output, taken on trust and bound by the export hash.
  - Plan task for FE1e: check each instance's and default instance's class against its type's conclusion, with reducible unfolding as Lean does (DecidableEq needs it). Keep the printed-back statement as the remaining guard for the rest.
- L1 ([import]): with `--snapshot BASE --snapshot LAYER`, the hash checked is the base's (snap-export-sha of ck-snap, check-lf.fs:139), while names resolve in base and layers (ck-snap-base loads the layers into the same stage). A record naming a layer's declaration therefore passes as data of the base export. Either refuse --elab-data with layers (`ck-layers# 0<>`) until a layered format exists, or bound declaration numbers by the base's count.
- L2: lfc-elab-read's failure branch (check-lf.fs:141-142: the library cannot be hashed again with --no-manifest) sets lfc-elab-failed without an elaboration error code. cli-elab-error then prints "refused at line 0 (error 0): none".
