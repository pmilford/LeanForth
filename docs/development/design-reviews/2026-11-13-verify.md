# Design review of VERIFY_COMMAND (8.4.1), 2026-11-13 — blocking for V1

Reviewer: independent design reviewer (Opus), read-only; first review under the owner's design-stage decision of
2026-11-13 (plan 9.4.7). This AI review does not replace the owner's gates.

**Verdict.** The shape is right: LeanForth's checker is the only judge; CHECK, VERIFY and RUN separate; results say
"discharged" or "NOT VERIFIED", never a bare "verified"; compiled code never claimed. One blocking hole: the contract
file can put arbitrary Lean into the generated file; the reviewer made pinned Lean accept a false contract that way.

## Blocking

**B1 (§3.2 rule 3, §4 step 3, §5, §15 risk 1): contract text reaches Lean unparsed, so V1 can report `discharged` for a
false contract.** program_vc.py (verify-b :1110; main :1061) writes `/-- {statement} -/` with the statement taken raw
(:334, :346). Test: clamp with `ensure value = 5 && lower = 0 && upper = 9 -> r >= 6` (false: clamp leaves 5) and the
statement line `… -/ macro_rules | \`($a ≥ $b) => \`($a ≤ $a) /-- …`: the generator says discharged (its search never
tries value 5); pinned Lean exits 0 with warnings as errors; O1, O2 and `contract` use only allowlisted axioms. In a
first variant Lean's own `#print post` shows `→ r = r` while the generator text, `--detail` and the receipt's statement
show `r >= 6`; the program print-back is untouched; LeanForth checks proofs against their statements, so it would
accept (not run). The same channel can redefine ∧/∃ in `contract` and take over tactic macros — "a proof of True under
the expected name" again, through the contract file; a correct contract can also be made refuted. Fix in b: no contract
text enters Lean except the expression parser's output (drop the statement from the Lean file; it is in the receipt);
refuse `-/`, `/-` and control or format characters in the statement, the word and the paths; a test that the generated
file is the same apart from one comment for any statement, a hostile corpus, a planted fault; take `contract.post` /
`--detail` from Lean's own print in this run, hashed in the evidence; the exported `ProgramVC.<Id>.*` names exactly the
generator's set. Files: /tmp/claude-1000/-home-peter-code-LeanForth/69a89404-3a7f-48aa-b333-1f7651c5eb48/scratchpad/
drv/{evil.contract,gen.py,evil.lean,evil.out}.

## High (before V1's gates)

**H1 (§4 l.226, §5 l.258, receipts A7): [bypass] scope and an unchecked translation.** The clamp approval covered one
committed, reviewed generated file; V1 trusts a new file per contract no one reviews. Receipt A7
(program_receipt.py:263-267) calls the generator "safe" for the program side only; nothing says `post` is unchecked. No
[parser] gate was ever held on contract 0.1 or its translation. Fix: an explicit owner question for V1's [bypass]; a
light [parser] gate on the Python operator table; an A7 sentence "the translation into `post` (file, sha) is unchecked;
what is proved is `post`"; a make-check differential of Python's `evaluate` against Lean's evaluation of each operator
on the 12 candidates, on cells64.

## Medium

- **M1 (§6.2, §6.5) exit statuses:** a LeanForth rejection of what Lean accepted is a checker disagreement (proposed
  `checkers-disagree`, exit 5), not exit 1; a receipt with check `rejected` stays honest. bin/leanforth:23-28 treats any
  status other than 100+code as internal; Python's uncaught exception exits 1 ("refuted/rejected" here) — the wrapper
  must map it to 5.
- **M2 (§4 step 6):** the driver never checks the check report's `schemaVersion` (program_verify.py:570-585);
  check-json.fs:48 writes 0.5 for snapshot runs: require 0.4 and no `snapshot` member, so only final runs give receipts.
- **M3 (§7 l.398):** the receipt does not hash the evidence record (program_verify.py:723-724), so a receipt and
  evidence changed together replay clean and only `--replay --rerun` re-establishes a verdict: say so, and hash the
  evidence. LEAN/LEANEXPORT from the environment (program_receipt.py:611-614) let a substituted exporter write any
  statement while the receipt names "Lean 4.35.0": the user command should ignore them (test hook only) and record the
  binaries' SHA-256.
- **M4 (§3.2, §11 class 2) contract pitfalls:** zero cases give `post := True` (program_vc.py:872); cases missing some
  inputs or an unsatisfiable `pre` are silently weak or vacuous; repeated id/word lines overwrite (:345-346) though §11
  says refused; unbound identifiers go out verbatim (:325, :714-715); `default` becomes 0. Fix in b: refuse these; the
  search notes "no candidate meets pre" and "inputs no case covers".
- **M5:** stage names v0/v1/v2 clash with slices V1-V4; rename and re-cut §12 into V1-V4 with acceptance commands, tests
  and docs in the slice.
- **M6 usability:** the `ir` line must equal the IR byte for byte and nothing tells a user how to make it (add
  `--write-ir`, or contract 0.2 with an optional `ir` line, in V1); V1 works only inside the checkout (0.5's project
  paths into V2).
- **M7 work in flight:** verify-b changes program_vc.py (clamp receipt's evidence hash), program_receipt.py,
  faults.toml; adds two ~100 s LeanForth runs to `check:` beside program-clamp-record's ~100 s on the same 4,277
  declarations (far over the documented ~45 s); B1 touches program_vc.py again (regenerate once); step c edits
  src/cli/leanforth.fs, also changed by fe1g3, snap-compat and snap-compat-c4. Consolidate: clamp's record from
  verify's single run, or document two clamp receipts (RUN passed vs not run).
