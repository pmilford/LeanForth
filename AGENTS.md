# Agent instructions — LeanForth

Read `docs/project/CODEX_HANDOFF.md`, `docs/project/IMPLEMENTATION_PLAN.md`, `docs/programming/INTERFACE_CONTRACTS.md` and this file before making architecture changes. Treat this as a formal-methods and systems-programming project, not a normal code-generation project. For the current state and next step, read `docs/project/PROJECT_PROGRESS.md` (its "Now, next, later" list is the near-term queue). This file is shared by all coding agents: Codex reads it directly and Claude Code loads it through `.claude/CLAUDE.md`.

## Non-negotiable design decisions

- The goal is a finished, usable LeanForth product: a Lean- and Mathlib-compatible theorem prover and a checker for provably correct executable Forth programs. Experiments and prototypes are temporary development stages, not the intended deliverable; carry work forward toward production-quality implementations, documentation and tests.
- Mathlib compatibility means the ability to use the full Lean Mathlib library, not merely selected theorems or a representative subset. Maintain the full-library goal while tracking incomplete Lean features, dependencies, scalability and review requirements honestly.
- The canonical language is ordinary Forth tokens and words; mathematics is represented as typed AST/data. Mathematical brackets, subscripts and infix symbols belong to an external notation/editor/rendering layer, not the canonical Forth grammar.
- The project must develop **two equally visible product paths**: theorem proofs and verified executable Forth programs. Each early milestone should show both if technically feasible.
- Small **trusted kernel** checks all proof terms. Parsers, LLMs, tactics, proof explanations, MathJSON/LaTeX adapters, solvers, fast compilers, GPU backends and tensor libraries are **untrusted** and can never confer theorem validity.
- Never make an unchecked theorem true by asserting it as an axiom, treating a failed check as success, bypassing the kernel, or silently changing the specification. Preserve an explicit, audited axiom allowlist.
- Program correctness means correctness against **stated semantics and assumptions**. Compiled code and external numerical backends are not automatically verified by a proof of the source program. Report assumptions, trusted runtime boundaries, floating-point caveats and any incomplete backend validation.
- LLM-facing APIs must be versioned, deterministic where practical, documented with JSON Schema and structured error codes, scriptable and operable without chat/UI.
- Proof steps should carry source IDs and derivation/certificate references. Explanatory prose is not a substitute for checked derivations; tag reconstructed or LLM-generated explanations clearly.
- Tensor work must use explicitly typed shapes, strides, element types, ownership/lifetimes, memory placement and effect/aliasing contracts. CPU fallback is mandatory; never put a GPU in the trusted kernel.
- Prioritize portability: Forth-2012 core compatibility, Gforth 1.0 as a development host, Linux/WSL CI, and architecture-independent serialized terms.

## Work process

- **Follow the critical path.** Take the next step from the "Now, next, later" list in `docs/project/PROJECT_PROGRESS.md` (it replaced the roadmap's near-term queue on 2026-11-12) and keep that list dated and current; `scripts/push.sh` refuses a push whose plan status changes are newer than it. Keep both product paths visible there: when one is parked, say so. Prefer finishing, consolidating, promoting or retiring existing experiments over adding new probes, diagnostics or another variant of an existing operation; a new experimental module needs a stated purpose on the critical path.
- **Do not build around a gate.** When the next critical-path step is blocked on a human-review gate or a user decision, stop, state the specific open questions in plain language with a recommendation and reasons, and ask the user. Further work around the gate is not a substitute for the decision.
- Update `docs/project/PROJECT_PROGRESS.md` in the same commit whenever a roadmap task or milestone changes status. Give the full report — both approximately ten-milestone tracks, their overlap, NDJSON support, code inventory, and relevant verification and limitations — at the end of a work session or when asked, not in every commit.
- **Test by what a change reaches, and never re-test an identical tree** (owner, 2026-11-13; `docs/project/OWNER_DECISIONS.md` "Less repeated testing", plan 9.4.6). While working, run only the focused tests of what you change (`make test-changed`; `docs/development/TESTING_STRATEGY.md`, "Running the suites"). Each branch runs its change tier's suite once, at the end, on the head it hands over, after rebasing on main (`make tier`, which records each pass for the tree and reuses a recorded one): documentation only — the documentation and progress checks; tests only — the changed tests, their faults and the coverage of the files they test; a library nothing loads yet — its tests, its faults and coverage; front end — its targets and the files it loads; kernel, core, import, cli, the Makefile or scripts — the whole of `make check` (Forth and Python tests plus every pinned-Lean comparison, about 45 seconds locally with the shared Lean cache, about 75 seconds with `LEAN_CACHE=0`; much longer at `JOBS=2`) and `make coverage-check`. A tier never skips a test of a file the change can reach. Do not run the suite again after a review fix unless the fix reaches a file outside the tier, and never re-run a suite on a tree that already passed it with the same Gforth and Lean: reuse the recorded result. Gforth 0.7.3 runs at the push (`scripts/push.sh`), not in a branch's tier (owner, 2026-11-14); the full suite, Gforth 0.7.3 included, runs once a day with `LEAN_CACHE=0` and before every tag. Install pinned toolchains with `scripts/install-gforth.sh` and `scripts/install-lean.sh`.
- **Design before code, and review the design** (owner, 2026-11-13; `docs/project/OWNER_DECISIONS.md` "Design stage", plan 9.4.7). A design has a main text of about 300 lines (Lean-source notes and long tables in an appendix), one per milestone where practical, and is cut into slices that each end in a command a user can run, with their tests and documentation in the slice. Before code starts, an independent reviewer (not the author) reviews it against the checklist in `docs/development/DESIGN_STAGE_REVIEW.md` — Lean fidelity of functions and data structures, what the next layers need, work in flight on the same files, slices, trust and gates, size, the owner's questions — and the owner approves a one-page summary. Kernel designs also keep the ADR gate below.
- **Size work by a user-visible result** (owner, 2026-11-13): a plan step is something a user or the next layer can use, not one layer at a time; a new library lands with its first real caller in one branch (libraries the owner asks for on their own excepted); coverage allowances and small follow-ups go into the branch that caused them. Group roughly two related, independently reviewable increments into a work batch before running the tier's suite and committing, when practical. Keep focused tests close to changes, run all required checks before committing, and checkpoint sooner when needed to protect work or isolate a failure. Do not batch across human-review gates or delay a necessary CI fix.
- **Nothing is called done until the done checker says so** (owner, 2026-11-12, after work was repeatedly reported done that was not integrated). Status uses the stages of `docs/development/DONE_CHECKER.md` (designed, written, tested alone, integrated, works end to end, done). Before a plan row, milestone, progress report or message to the owner calls work done, the independent done checker (`.claude/agents/done-checker.md`, `.codex/agents/done-checker.toml`) must run the user-facing command on the real input the claim implies and report DONE; cite its report in the plan row. Say exactly what was run: today LeanForth re-checks proofs that Lean produced and exported; until LeanForth text is checked by the kernel (plan 8.2.1c), never write that LeanForth proved a theorem or show LeanForth text as runnable input.
- **Report progress to the owner in one form** (owner, 2026-11-12): (1) what a user can do now that they could not before, with the command; (2) what changed, by stage; (3) what still does not work; (4) questions for the owner. Every "works" or "done" names the command that was run or the done-checker report. **Push only with `scripts/push.sh`**, which runs the progress check, the Forth review and style check, and both CI jobs, records the results and refuses to push on any failure.
- Use not-started, in-progress and done for milestones and named subtasks; report completed/in-progress/remaining counts against the roadmap's acceptance criteria. Periodically report evidence-based NDJSON and full-Mathlib percentages with a clear denominator; distinguish checked-declaration coverage from estimated effort, and say unknown when no denominator exists. GitHub CI is turned off at the owner's request (2026-11-11): before every push, run CI's two jobs locally under `ulimit -u 500` — `make check` on pinned Gforth 1.0.0 and Lean 4.35.0 (with `LEAN_CACHE=0` at least once a day and before a tag) and `make test` on Gforth 0.7.3 (`scripts/push.sh` runs them by change tier, `make test` once under coverage in the full tier: `make coverage-check` and `make check-rest`) — investigate failures, and record the outcomes; re-enable GitHub CI (`gh workflow enable CI`) only when the owner asks.
- **Tests to the owner's "110% coverage"** (`docs/development/TEST_COVERAGE_REVIEW.md`): every new or changed word gets tests in each applicable class — pass and fail with every outcome, malformed input, interfaces and stack effects, whole workflows and I/O, resources and exhaustion, state and rollback, regression pins — and a planted fault in `tests/mutants/faults.toml` for each risky word, which a test must catch. Block coverage (`make coverage`) may not drop: the coverage ratchet (`make coverage-check`, in the full tier) fails when a file's never-run blocks grow. A change without these tests is not done (`docs/development/DONE_CHECKER.md`).
- Develop and maintain user manuals, installation, contributor, testing and interface documentation alongside each feature; distinguish implemented behavior from plans and state trust boundaries. Keep docs/user/LANGUAGE_REFERENCE.md current in the same branch as any change to a LeanForth word (owner, 2026-11-15).
- Plan and maintain audience-specific documentation for Forth developers and users, Lean users, mathematicians with or without Lean experience, and AI tools; explain terms such as level, Sort, theorem and kernel. In user documentation, show each concept or example as a concrete, slightly non-trivial instance in three forms: mathematical notation, LeanForth Forth syntax and Lean. Create and carefully check flowcharts for theorem and program verification workflows, internal architecture and principal data structures, using a diagram tool and verifying rendered diagrams. Document actual supported scope and measured size, depth, compute and memory limits and distinguish plans from implemented behavior.
- Use scoped independent subagents when they materially improve parallel work or reviews, especially for Lean, Forth and kernel integrity. Measure usage where feasible; subagents do not necessarily save tokens and cannot replace required human review. Agent definitions live in `.codex/agents/` (Codex) and `.claude/agents/` (Claude Code); keep equivalent definitions in sync.
- Put Forth source in the `src/` folder that matches its role, as `src/README.md` describes: general tools in `lib/`, Lean's data model in `core/`, the checker under development in `kernel/` (trusted only once the owner declares it so after the review gate below), and every current module in `src/main.fs`. The superseded variants once kept in `src/legacy/` were retired on 2026-11-02; never re-add a superseded variant or build on an old copy of a current module.
- Write general-purpose functionality — big numbers, JSON reading and writing, hashing (SHA-256), byte and UTF-8 reading, 32-bit access, stores and hash tables, the job pool — as well-factored, standalone libraries that other Forth programs can load and use, not coupled to LeanForth (owner, 2026-11-03): each file requires only what it uses, keeps its helpers private (ADR 0010), documents its interface with an example, and has tests that run outside the checker. Make a library LeanForth-specific only where that gains a lot, and say why in its header.
- **Reuse first, and write code as an experienced expert would** (owner, 2026-11-13, after a reviewed stable sort in `src/lib/sort.fs` sat unused while new front-end code hand-wrote an insertion sort, and the library candidates of the 2026-11-12 backlog reviews were never extracted: "this is really a bad problem and should never happen … code like an experienced expert programmer, not a beginner … write reusable high quality code"; plan 9.4.8). Write reusable, well-factored code of the quality an expert Forth and systems programmer would sign: no hand-written copy of an operation that already exists, no general operation buried in a module, no speculative library left without a caller. Concretely:
  - **Before writing a word, look for it.** Search `src/lib/` (its inventory in [FORTH_LIBRARY.md](docs/development/FORTH_LIBRARY.md) and `src/README.md`) and the modules beside the change for a word that already does the job, and use it. Never hand-write a sort, a hash table or search table, a map, a heap, a stack or frame for a non-recursive walk, a memo cache, a growable array, a bounds check, an outcome chain, a parser or a printer helper that a library or another module provides.
  - **When something general is missing, write the library first.** A general operation that two places need, or that one place needs and no library has, becomes a standalone library (the rules above, ADR 0010) or a shared module word, with its own tests and faults, and every existing copy in `src/` is replaced in the same branch (kernel copies under the kernel's review gate). A library a review proposes is a plan task in a named slice, never only a note in a report.
  - **Designs and briefs name their libraries.** Every design has a "Reuse" part — the libraries and shared words it uses, the new ones it needs and the copies they replace — which the design review checks; every implementation brief names them, and the implementer's report lists each general-purpose helper it wrote and why no existing word served.
  - **Reviews block on duplication.** The Forth reviewer treats re-implemented functionality (of `src/lib/` or of another module) and a library with no caller as findings that block the merge until fixed or planned with a slice.
  - **Every library documents its profile** (owner, 2026-11-13), as [FORTH_LIBRARY.md](docs/development/FORTH_LIBRARY.md#sorting) does for `sort.fs`: the algorithm and why; how generic it is (the caller's comparison, key or record size; what it assumes of the data); its cost as inputs grow, small and large (cut-overs, scratch memory, recursion depth); its measured speed at a small and a large size; and its callers with the sizes they actually pass, measured on a real run (Init, Mathlib), updated when a caller is added. A library without this is not done.
- Document Forth modules and public words with readable comments, including stack effects, behavior, error cases and relevant assumptions. Explain non-obvious implementation details where helpful.
- Treat Forth as its own language: write clear, idiomatic, concise and well-factored words with simple stack effects, following `docs/development/FORTH_STYLE.md` — words of one or two lines, data on the stack rather than in global variables, named structure fields, dispatch tables, one shared outcome vocabulary. Prefer small composable words and meaningful Forth names; do not mechanically translate another language or sacrifice readability, safety or performance to minimize word length. **Every change to Forth source is reviewed by the independent Forth reviewer** (`docs/development/FORTH_REVIEWER.md`) before it reaches `main`: its report is saved in `docs/development/forth-reviews/` and logged in `LOG.md` there, and `make test` fails on `main` for a commit after `3ac0558` that changes `src/**/*.fs` without a logged review (`scripts/check-forth-quality.py`; owner, 2026-11-12, after reviews had silently stopped). Fix each finding before the merge or record it as a plan task. The same check holds a style ratchet (`tests/forth-quality-baseline.json`): per file, long words, deep stack shuffles, return-stack operations, globals and long lines may not grow except in a reviewed commit that raises the baseline, and a new file starts at zero long words and below the project's shuffling average. Implementing agents run `python3 scripts/forth-metrics.py` on every Forth file they change. Correctness reviews of the checker never replace this style review, and saving tokens is never a reason to skip it.
- Preserve the profiling and research-validation tasks in `docs/project/DEVELOPMENT_ROADMAP.md`: lightweight optional time and memory measurement and fair Lean comparisons; later reproduce several substantial published Lean results and a longer recent theorem, then investigate an appropriately chosen open problem with transparent proof status.
- Divide later work into narrowly scoped issues and test-first changes. Keep a running `docs/project/DECISIONS.md` with rationale and rejected alternatives.
- Before changing kernel semantics: propose an ADR; add positive/negative tests that reach every outcome (accepted, rejected, unsupported/unknown); compare with pinned Lean 4.35.0 on available cases; then complete the review gate below. Do not merge kernel changes solely on LLM review.
- Do not claim a check/benchmark/platform test was run if it was not actually run. Document missing tools and blocked tests.
- **Commit and push automatically.** The owner is currently the only developer and there is no pull-request reviewer. To protect against crashes and lost work, commit work on its branch as it goes, and push to `main` of the existing GitHub remote at checkpoints — about every two to three hours, at the end of a work session, or when a branch someone needs lands — without asking each time (owner instructions, 2026-11-02 and 2026-11-13); documentation-only commits ride with the next push. Run CI's two jobs locally before the push, as described above (a pass recorded for the identical tree counts, plan 9.4.6). Never force-push or rewrite pushed history.
- User approval is still required for GitHub authentication, remote creation or changes, external service authorization, destructive actions, installing system packages with privilege, and adding new runtime/network dependencies.
- Never delete files or directories that were not explicitly planned. Ignored, machine-local directories such as `.tools/` are user data. List exact paths before deleting and delete only those paths by name; never run a dry run and the real deletion in one command, and do not use pattern-based cleaners such as `git clean -X`.
- Record all commands used, observed versions, exact CI status and reproducibility hashes. Do not commit secrets, private keys or credentials.
- Use `scripts/check-env.sh` to collect a safe, read-only inventory of the development environment.

## Review gates

Kernel integrity, declaration import, proof certificate formats, new axioms, verifier bypasses, compiler/FFI assumptions and mathematical parser semantics require explicit human review. All malformed-input tests must fail closed. Maintain at least one acceptance test that constructs a valid proof and one that rejects an invalid proof, once the minimal kernel exists.

The project owner is not a Lean expert. Under the owner's decisions of 2026-11-02 (`docs/project/OWNER_DECISIONS.md`), human review of a checker change means all of:

1. The rules follow Lean's own published kernel behavior; do not invent new typing or conversion rules.
2. Pinned-Lean differential tests agree, including deliberately invalid or mutated proofs that must be rejected, and tests reaching each outcome: accepted, rejected and unsupported/unknown. No failure outcome may ever be reported or stored as accepted.
3. An independent AI review of the exact change records no unresolved findings.
4. The owner approves a short plain-language summary of the change: what it does, the evidence, the risks and a recommendation with reasons.

Results carry no "experimental", "not independently audited" or "pre-alpha" label (owner, 2026-11-12, replacing the label rule of 2026-11-02); an outside Lean-expert audit is still planned (plan 9.2.1), and status wording must still say exactly what was run. Axioms: none for the first checker; later only `propext`, `Classical.choice` and `Quot.sound` with their exact Lean statements, in a versioned allowlist the owner approves; never `Lean.ofReduceBool` or `Lean.trustCompiler`. Report each accepted theorem's axiom dependencies. Ask the owner every gate question in plain language with a clear recommendation and reasons.
